# 项目总纲

[English](./project-charter.md) | [简体中文](./project-charter.zh-CN.md)

## 使命

Kedoupi Pi Plugins 是一个可信的 Pi Package 发现与发行体系：既是独立 `@kedoupi` 第一方 Package 的开发中心，也是共享开发规范入口和人工精选的公开社区 Package 目录。

目标不是收集最多的插件，而是让每一项公开声明、安装路径和维护决策都可以被理解和验证。

## 范围

本仓库提供：

- 位于 `packages/` 下的独立第一方 Package；
- 开发、测试、安全和发布规范；
- 带有双语调研说明的第三方精选目录；
- 确定性的仓库门禁和自动生成的 Catalog。

仓库根目录是私有工作区基础设施，永远不是可安装或可发布的 Pi Package。Kedoupi 可以记录和评价第三方 Package，但不重新打包其源码，也不把它们加入第一方 Suite。

## 非目标

项目不会在真实第一方 Package 需要它们之前创建占位 Package、空 Suite、推测性抽象或发布自动化；不会镜像第三方仓库、承诺绝对安全，也不会把公开文档调研描述成功能测试。

新增基础设施必须源于已经出现的需要。真实流程至少完整走通一次后，才将其提炼成模板、Suite、Skill 或更广泛的抽象。

## 工作原则

1. **真实价值优先于表面完整。** 明确承认缺口，胜过制造虚构产品。
2. **先有证据，再做声明。** 调研、实际执行、敏感操作审阅、兼容性和安全性是不同声明，需要不同证据。
3. **适合自动化的政策应成为代码。** 确定性规则进入离线校验；需要判断的事项仍由维护者负责。
4. **拥有第一方产品，但不占用第三方成果。** 始终保留上游作者、许可证、链接和维护边界。
5. **标准库和原生工具优先。** 新依赖与新自动化必须证明其长期成本合理。
6. **独立发布单元。** 每个第一方 Package 拥有自己的版本、CHANGELOG、测试、Tag 和 Release。
7. **安全表述保持保守。** `tested` 和 `reviewed` 永远不代表零风险。

## 证据模型

Catalog 状态是一条证据阶梯，不是热度排名：

- `community`：已调研公开元数据与双语文档，并通过仓库校验。
- `tested`：维护者使用所记录的 Pi 版本，实际安装并使用过所记录的 Package 版本。
- `reviewed`：在 `tested` 基础上，进一步检查入口、权限、文件、网络、凭据、子进程或其他敏感行为。
- `deprecated`：由于来源、维护状态、信息准确性或适用性不再满足 Catalog 政策而不再推荐。

维护者的本地 Package 清单只是发现候选的信号，不是 Catalog 成员清单的镜像。新安装的 Package 必须先调研再决定是否收录；本地卸载也不会在缺少维护状态、信息准确性或适用性证据时自动撤销推荐。

仅仅安装在本机或审阅公开文档，都不会自动产生测试证据。状态升级必须符合维护者证据要求，详见 [Catalog 政策](./catalog-policy.md)。

## Package 生命周期

第三方 Package 的流程是：

```text
公开候选
→ 核对来源、许可证和元数据
→ 编写双语详情并披露风险
→ 离线校验
→ community
→ 隔离环境功能测试
→ tested
→ 敏感操作审阅
→ reviewed
→ 必要时 deprecated
```

第一方 Package 的流程是：

```text
确认真实用户需求和稳定名称
→ 在独立 workspace 中实现
→ 项目级加载和自动化门禁
→ 用全局本地源码完成真实任务 dogfood
→ 独立 npm 发布
→ 验证安装、更新、卸载和回滚
→ 按需加入第一方 Suite
```

具体执行要求见 [开发流程](./development.md)、[测试政策](./testing.md)、[发布政策](./publishing.md)和[第一方 Package 标准](./package-standard.md)。

## 自动化与安全边界

仓库 CI 必须离线、确定性执行；Node.js 标准库足够时不增加依赖。CI 负责验证仓库自有的结构、元数据、文档契约、生成结果和 Package 内容，不负责自动爬取网站、同步数据库、调用付费服务，也不会仅因调研日期较旧就判定信息失效。

仓库不得包含密钥、`.env` 文件、私有清单、真实凭据、Cookie 或本机专属路径。Pi Extension 以当前用户权限运行，因此文档必须披露相关的文件、网络、凭据、子进程和付费服务行为。

## 决策权

社区贡献者可以推荐 Package，并提交 `community` 元数据。Catalog 是否收录、基于证据的状态升级、弃用、第一方 Package 选择、Suite 成员关系和所有发布操作均由维护者决定。发布始终需要维护者明确确认。

## 当前状态与下一道门槛

仓库基础设施和双语 Catalog 流程已经得到验证。Catalog 当前收录的是公开社区 Package，不声称这些 Package 已由 Kedoupi 完成功能测试。

第一方 Package 生命周期已经完成设计，但尚未端到端验证。下一道门槛是选择一个具有真实用户价值和稳定名称的 Package，完整完成项目级测试、全局 dogfood、发布、安装、更新、卸载和回滚。Suite、可复用的 Package 开发 Skill 和发布 workflow 继续推迟，直到这个真实流程证明它们有必要存在。
